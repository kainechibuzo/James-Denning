# JD-231 — Reduce JD model round trips and instrument latency

- **Created (UTC):** 2026-11-13
- **Owner/request source:** User request to target model latency, sequential model requests and time-to-first-response without destabilising the live pipeline.
- **Status:** in_progress
- **Priority:** high
- **Related PR/issue:** Pending CI and review.
- **Related commit(s):** `aed9e6593d4eea614eb175fa7afb2fdb502ae61b`, `c22f9a072594777830481f81b550ce6e3238b806`

## User outcome

JD should avoid unnecessary model round trips, keep a free-router conversation on the model selected for its first turn, and expose per-request latency so slow models can be measured instead of guessed.

## Scope and acceptance criteria

- [x] Batch independent read-only tool requests in a single parallel tool-call round when appropriate.
- [x] Pin subsequent tool-call rounds to the first model selected by `openrouter/free`; preserve explicitly configured model choices.
- [x] Record per-request model latency alongside provider-reported usage and model identity.
- [ ] Deno runtime tests and secured Edge Function type-check pass in CI.
- [ ] Staging smoke test confirms model pinning, checkpoint resume and persisted latency telemetry.
- [ ] Compare at least five representative runs before selecting a fixed free model or changing provider routing.
