# JAMES DENNING
## Product Feature Sheet — Autonomous Business & Software Platform

**Version:** 1.0  
**Date:** November 2026  
**Product:** James Denning (JD)  
**Category:** AI-powered Business Operating System and Software Creation Platform

---

## 1. Product Vision

Transform James Denning into an intelligent business operating platform where anyone can bring an idea, build an organisation around it, create the software it needs, connect the tools it uses and manage its operations through JD.

**Core promise: Run. Monitor. Build. Grow.**

JD is the central intelligence and execution layer of James Denning. It should understand business requirements, design solutions, coordinate specialised agents, execute authorised work and verify outcomes.

The platform must support different kinds of organisations without forcing them into one fixed structure.

## 6. MCP Connector Ecosystem

JD should have a connector catalogue containing integrations that customers can discover, connect and use. JD should also recommend integrations automatically based on what customers are trying to achieve.

**Important distinction:**

- **Connector catalogue:** integrations available for customers to discover.
- **Connected MCP servers:** integrations a particular customer has authorised.
- **Discovered MCP tools:** actual tools exposed by a connected server.

A connector appearing in the catalogue does not mean it is connected or ready to execute.

### Connector verification requirements

Before a connector is marked available, JD should establish:

- Whether an official integration exists.
- Whether it uses MCP, OAuth, an API or another supported connection method.
- Its authentication requirements.
- Its available capabilities.
- Its required permissions and scopes.
- Its security and maintenance status.
- Whether its tools have been tested.

Do not represent an ordinary API integration as an official MCP server.

## 7. Intelligent Connector Recommendation Engine

JD should recommend connectors when it identifies a genuine requirement.

### Example: Customer requests a school website

Customer:

> I want to create a website for my school.

JD should:

1. Understand the website requirements.
2. Research the school and its target audience.
3. Create a website architecture.
4. Inspect already-connected integrations.
5. Identify missing integrations.
6. Recommend relevant connectors.
7. Explain why each connector is useful.
8. Allow the customer to authorise the connections.
9. Start the development process.

### Example connector recommendations

| Connector | Importance | Reason |
|---|---|---|
| GitHub | Recommended | Source code and version control. |
| Lovable | Optional | Rapid website or application scaffolding. |
| Vercel | Recommended | Website previews and deployment. |
| Supabase | Conditional | Needed if the website requires a database, authentication or dynamic applications. |
| Google Workspace | Optional | Useful for school communications and document workflows. |
| Paystack | Conditional | Needed if the school wants online payment collection. |

JD should not overwhelm customers with irrelevant integrations.

Every recommendation should explain:

- What the connector does.
- Why the customer needs it.
- What data it can access.
- What permissions it requires.
- Whether it is required or optional.
- Whether the customer already has it connected.

**Customers must explicitly authorise connections.**

## 8. JD Software Factory

This feature turns JD into a software creation platform.

Customers should be able to describe a website, application, dashboard or internal business tool and have JD plan and build it.

### 8.1 Software Creation Capabilities

| Feature | Description |
|---|---|
| Website Generation | Creates customer-facing websites. |
| Web Application Generation | Builds functional web applications. |
| Dashboard Generation | Creates business-specific dashboards. |
| Landing Page Generation | Creates marketing and conversion pages. |
| Backend Development | Builds required backend functionality. |
| Database Architecture | Designs database schemas and relationships. |
| Authentication | Implements appropriate user authentication. |
| API Development | Creates application programming interfaces. |
| Responsive Design | Supports desktop, tablet and mobile layouts. |
| Testing | Runs appropriate automated tests. |
| Security Review | Checks for common application security issues. |
| Code Management | Maintains code in GitHub repositories. |
| Deployment Preparation | Prepares applications for deployment. |
| Preview Environments | Allows customers to review applications before release. |
| Deployment Verification | Checks whether the deployed application is functioning. |

### 8.2 Three Development Routes

JD should select the most suitable development approach.

**Route A: Lovable**

Use Lovable where its supported integration is suitable for rapid application scaffolding and initial development.

**Route B: GitHub**

Use GitHub to:

- Create repositories.
- Create branches.
- Manage source code.
- Commit changes.
- Open pull requests.
- Review code changes.
- Track project history.

**Route C: JD Native Coding Engine**

JD should also be capable of writing code directly.

It should be able to:

- Generate frontend code.
- Generate backend code.
- Build database schemas and migrations.
- Create APIs.
- Write tests.
- Fix bugs.
- Refactor code.
- Run builds.
- Review errors.
- Prepare deployment configurations.

JD must use an isolated development environment for generated code and must not execute untrusted code directly against production systems.

### 8.3 Development Lifecycle

1. Customer describes the project.
2. JD analyses requirements.
3. JD researches the market and relevant technologies.
4. JD prepares a technical architecture.
5. JD checks existing connectors and repositories.
6. JD recommends missing connectors.
7. Customer authorises required integrations.
8. JD chooses Lovable, GitHub, native coding or a combination.
9. Development agents build the project.
10. QA agents run tests.
11. Security agents review the application.
12. JD prepares a customer preview.
13. Customer reviews the result.
14. Customer approves deployment.
15. JD deploys through an authorised integration.
16. JD verifies the deployed application.
17. JD records the final evidence and project handover.

- Proposed
- Planned

## 14. Security and Governance

Autonomy must not mean unrestricted access.

Required controls:

- Server-side authentication.
- Tenant isolation.
- Role-based access control.
- Least-privilege connector permissions.
- Encrypted server-side credential storage.
- Explicit authorisation for external integrations.
- Approval for consequential external actions.
- Audit logging.
- Secure development environments.
- Code review and automated testing.
- Deployment approval.
- Execution limits and budgets.
- Tool input validation.
- Connector provenance and verification.
- Safe rollback procedures.

JD must never expose one customer's information or integrations to another customer.
