# James-Denning — Product Completion Roadmap

**Updated:** 2026-11-23  
**Baseline:** source implementation is substantial, but live operational evidence is materially behind it. The prior audit estimated **30–35% implemented against the full product vision** and approximately **20% operationally demonstrated**. These are planning estimates, not measured code-coverage metrics.

## Product outcome

James-Denning is an AI business operating system. A user describes a business outcome; JD understands the organisation, selects the right specialist capabilities, plans work, coordinates bounded agents, executes permitted actions, requests human approval for consequential actions, and verifies real outcomes with an auditable record.

The system must distinguish:

**proposed → saved → approved → executing → completed → independently verified**

An AI response, queued task, successful HTTP request, or completed internal job is not proof of an external business outcome.

## Delivery principles

1. Reuse the existing conversation runtime, durable execution worker, agent registry, skills pipeline, connector platform, billing foundation and operational modules. Do not rewrite working foundations.
2. Do not add disconnected feature surfaces. Every capability must be reachable from JD's request-to-outcome workflow.
3. Keep tenant isolation, least privilege, idempotency, audit events, cancellation and recovery as release requirements.
4. Skills and agent instructions are untrusted reference data. They never grant tools, permissions, spend authority or approval authority.
5. No agent may approve its own restricted action. Financial/legal commitments, hiring decisions/publication, external messages and deployments require the configured human approval boundary.
6. A green CI run or merged PR is not production acceptance. Require persisted records, runtime tests and independently reviewable evidence.
7. Keep production changes behind reviewed release gates. Do not use production as a staging environment or apply speculative migrations to it.

## Work remaining by programme

### 1. AI workforce and specialist routing — highest priority

**Audit baseline:** approximately 80% of the full workforce vision remains.

- [ ] Populate the agent registry with a reviewed, versioned initial specialist catalogue. Start with the existing eight built-in specialists; do not fabricate a 400-agent count.
- [ ] Connect JD intent classification to skill discovery, specialist selection and assignment creation.
- [ ] Make every assignment record the selected agent/version, skill/version, task scope, tool allowlist, budget, status and outcome.
- [ ] Add supervisor/coordinator behaviour: decompose objectives, assign specialists, track dependencies, reconcile results and escalate blockers.
- [ ] Add independent evaluation of actual assignment outcomes, not just registry contract checks.
- [ ] Define a safe catalogue expansion process toward 400+ specialists, with deduplication, capability tests, provenance and publication review.
- [ ] Verify live registry, skill publication, acquisition and run-reference records; source code alone does not count.

**Acceptance:** a real user objective selects the right specialist and skill, creates a bounded persisted run, produces a useful result, records provenance and audit evidence, and refuses unauthorised actions.

### 2. Autonomous execution and software factory

**Audit baseline:** approximately 90% of the full SaaS factory vision remains.

- [ ] Provide an isolated, disposable execution workspace for code/build/test tasks.
- [ ] Implement explicit repository permissions and branch-scoped changes.
- [ ] Give software specialists real, narrow tools for inspect/edit/test; do not present read-only reasoning tools as a coding workforce.
- [ ] Add build/test result ingestion, artifact provenance and failure recovery.
- [ ] Require human approval before production deployment, destructive migrations or external release.
- [ ] Prove end-to-end issue → plan → branch → code → tests → review → approved deployment.

**Acceptance:** a synthetic application change is made in an isolated branch, tested, reviewed, and held for approval before any production action.

## Release gates

No production release for a programme until all are true:

- [ ] Correct branch and reviewed PR; no unreviewed direct production changes.
- [ ] Unit, integration and database contract tests pass.
- [ ] Tenant isolation, role denial, idempotency and audit tests pass.
- [ ] Migration has an explicit rollback and is tested against an isolated database.
- [ ] Edge Functions are deployed at the reviewed commit and live versions confirmed.
- [ ] Authenticated runtime smoke tests pass.
- [ ] Persisted records prove the expected state transitions.
- [ ] Logs and failure paths have been inspected.
- [ ] Owner-facing UI accurately distinguishes drafts, approvals, execution and verified outcomes.

## First implementation sequence

1. **Workforce activation contract:** inspect current feature flags, registry schema, built-in specialist definitions, runtime wiring and deployment versions. Make the eight existing specialists discoverable through the same registry/selection path; do not seed fictitious agents.
2. **Request-to-specialist vertical slice:** one end-to-end synthetic objective through JD → discovery → skill resolution → specialist run → persisted result → audit/read-back.
3. **Execution tools:** introduce a sandboxed tool adapter for real task work, initially read-only; add write tools only behind branch-scoped permissions and approval.
4. **Live release verification:** reconcile code, migrations, Edge Function versions, flags and persisted records before enabling any feature.
5. **Commercial and executive programmes:** only after workforce execution is proven.

## Audit baseline and caveats

The 2026-11-23 audit observed meaningful source foundations: conversational runtime, durable worker, agent registry/engine, skill ZIP pipeline, connector platform, billing source, hiring modules, and business operations tables. However, the live database had zero agent definitions, published skills, skill versions, acquisitions, playbooks and connector grants; connector tool inventory was not equivalent to authorized integrations. The custom billing functions/migrations were not confirmed live. The executive coordinator was not present. These observations must be rechecked before each release because production state can change.

Estimated remaining effort by area from the audit (planning estimates, not measured code percentages): workforce 80%; SaaS factory 90%; connectors 65%; billing/agent payments 85%; recruitment 85%; CEO/executive oversight 100%; continuous operations 75%; business operations 35%.

**Operating rule:** finish and prove one vertical slice at a time. Do not inflate progress by counting scaffolding, draft records, catalog entries, or simulated execution as completed capability.
